# Mallowstead 0.1.4f-playtest1 — Authored Grounded-Item Policy, Character Throughput Routing, and History-Control Cleanup

## Status

Implementation specification.

Base: `0.1.4e-candidate3`.

Target version: `0.1.4f-playtest1`.

Authored Mallowstead world content for the grounded-item policy is specified separately in `docs/world/0.1.4f-playtest1-grounded-item-policy.md`.

This candidate adds one new authored world-level model policy, changes Character-provider routing from latency-first to throughput-first, and removes the unused SugarCube back/forward controls from the player UI.

---

# 1. Goals

1. Give world authors an explicit way to tell Character models which semantic categories of objects are **mechanically grounded** and therefore cannot be invented or mechanically manipulated through narration alone.
2. Preserve free narrative props outside those authored categories.
3. Make the grounded/narrative distinction model-facing without introducing deterministic natural-language parsing, automatic ontology inference, or secret-item enumeration.
4. Prefer OpenRouter provider **throughput** for Character-role requests while leaving Utility/Narrator routing unchanged.
5. Remove the SugarCube back/forward history controls from the visible player UI without changing Mallowstead's own narrative-history UI or save/persistence semantics.

---

# 2. Core ontology: grounded items vs narrative props

Mallowstead intentionally supports two fiction-layer object classes.

## 2.1 Mechanically grounded items

A mechanically grounded item is an object whose existence, identity, possession, placement, contents/state, trade/equipment state, or other gameplay-relevant state is owned by the engine.

A Character model may describe a grounded item, but narration alone must not:

- invent a new grounded instance;
- assume possession of one;
- take, give, transfer, place, drop, move, hide, reveal, fill, empty, consume, destroy, write on, equip, unequip, buy, sell, or otherwise mechanically mutate it;
- narrate a prerequisite tracked transition as completed merely because it would make the intended scene natural.

Such changes require a supplied formal action/result or other explicit engine grounding.

## 2.2 Narrative props

A narrative prop is an incidental fictional object outside the world's authored grounded-item policy and not supplied by the engine as a canonical item instance.

Narrative props may be freely introduced and manipulated in prose when appropriate to the scene.

Examples may include an incidental cup of herbal tea, a cloth, a spoon, generic kitchen clutter, or another ordinary detail that the authored world deliberately does not model mechanically.

Narrative props do not acquire canonical inventory identity merely because narration mentions them.

## 2.3 Fictional reality is not the distinction

Both classes are equally real inside the fiction.

`grounded` means only that the engine has claimed mechanical authority over that semantic territory. It is not a statement that narrative props are imaginary to the characters.

# 3. New authored world property

Add one optional top-level authored property to world documents:

```json
{
  "groundedItemPolicy": "Free-form author-facing/model-facing text describing which item categories are mechanically grounded in this world."
}
```

## 3.1 Shape

- Type: string.
- Optional for backward compatibility.
- Missing/blank means that no additional category-level item grounding policy is authored.
- Keep world `schemaVersion: 2`; this is an additive optional authoring field and does not require a save/world schema bump.
- The field is authored content, not mutable gameplay state.

## 3.2 Free-form by design

Do **not** replace this field with a structured list of item definition IDs, tags, families, or secret IDs.

The author must be able to write broad semantic categories such as:

- `keys and access-control items`;
- `clothing and jewelry`;
- `magical or supernatural objects`;
- `prepared food portions used by formal mechanics`.

This abstraction is intentional and may be used to protect secret semantic territory without revealing concrete secret instances.

## 3.3 Author responsibility invariant

The engine does not attempt to prove that the authored policy matches `itemDefinitions`, actions, tags, or world mechanics.

Authoring invariant:

> Any category whose instances must participate in engine-owned gameplay mechanics should be covered by the world's grounded-item policy.

Conversely, adding a category to the policy commits the author to supplying formal item instances/mechanics when characters need to manipulate members of that category. The model must not fill missing implementation by inventing instances narratively.

Example: if `keys` are grounded but a world author forgets to author a needed key instance, the correct model behavior is that the missing key is unavailable, not that the model invents one.

No warning/error is required for semantic mismatch in this candidate.

---

# 4. Concrete engine-supplied items remain grounded

The category statement extends grounding to semantic classes even when no instance is currently visible.

It does not weaken the existing rule for concrete canonical items:

> Any concrete item instance supplied by the engine through canonical view, inventory data, formal observations/results, relevant mechanics, or formal action options is mechanically grounded regardless of whether the broad authored policy happened to mention its category explicitly.

This is important for worlds that intentionally keep broad ordinary categories narrative while still having a few specific engine-tracked objects.

For example, a world need not declare all `tools` grounded merely because one specific canonical tool exists.

# 5. Character model context

## 5.1 Ordinary Character decision

Expose the authored string in ordinary Character decision context under a stable explicit field, suggested shape:

```json
{
  "worldAuthoredContext": {
    "groundedItemPolicy": "..."
  }
}
```

An equivalent narrowly named location is acceptable if it produces a cleaner existing context shape. Do not duplicate the same string in multiple places in one request.

The policy must be visibly labeled as authored world rules, not as a character memory or objective list of currently existing instances.

## 5.2 Other Character-owned narration contexts

Any Character-role request that can author scene narration involving objects should receive the same policy when practical through the shared context/helper path, especially:

- ordinary `game-decision`;
- Character daytime-job narration.

Do not add it to pure Utility retrieval/maintenance requests that cannot author physical scene behavior merely for consistency.

Narrator-role requests may retain their current contracts unless they themselves need the grounded/narrative distinction; do not broaden this candidate unnecessarily.

## 5.3 No secret-instance leakage

The policy is authored exactly as world content. The engine must not augment it by enumerating hidden item definitions, secret item IDs, hidden inventories, or undiscovered instances.

Secret protection comes from author-chosen abstraction, e.g. `jewelry and magical objects`, not from exposing `ironMedallion` or another hidden definition.

# 6. Model protocol rules

Extend the Character item/narration discipline with a concise explicit rule derived from the world property.

Required semantics:

1. Treat any engine-supplied canonical item as grounded.
2. Treat any item belonging to a category reserved by `groundedItemPolicy` as grounded even if no current instance is visible or accessible.
3. Do not invent an instance of a grounded category merely because the scene would naturally contain one.
4. Do not narrate a grounded item's tracked state change unless the corresponding formal engine action/result actually performs it.
5. **Absence from current inventory, accessible inventories, or `available_actions` means the Character cannot currently manipulate that grounded item. It never downgrades the item into a narrative prop.**
6. Narrative props outside grounded categories may be invented and manipulated freely when they do not claim tracked state.
7. Never reinterpret an already-grounded object as a narrative prop to complete an intended multi-step workflow.

The rule should be short and concept-first. Do not add a long duplicate list of every possible item verb if the new grounded-item distinction can state the invariant more clearly.

However, retain existing tracked-state/action-precedence safeguards in this candidate. Do not remove old prompt defenses yet; simplify them only after playtest demonstrates that the new ontology is reliable.

# 7. Garrick/Nell regression scenario

Add a regression fixture covering the playtest failure that motivated this change.

Relevant state:

- Garrick formally owns a tracked mug.
- Garrick performs only `fill`.
- Garrick's next intended step is `give_item` to Nell.
- Nell receives the observed narration/formal result but the mug is not in Nell's inventory or accessible inventories and no `take_item` is offered.
- The world grounded-item policy identifies tavern mugs/serving vessels as grounded.

The model-facing contract/context must make it unambiguous that Nell may **not** decide that the mug is an untracked narrative prop because it is absent from her accessible item surface.

Tests do not need to prove stochastic model compliance. They must prove that the decisive grounding information and protocol rule are present in the request context/contract.

Do not introduce deterministic parsing of `publicNarrative` to detect phrases such as `sets the mug down` or `picks up the mug`.

# 8. Authoring/editor support

Expose `groundedItemPolicy` in the world editor as a world-level multiline textarea, suggested label:

`Grounded item policy`

Help text should explain briefly:

- this text is sent to Character AI as a binding world rule;
- categories listed here cannot be invented/manipulated as narrative props;
- broad categories may intentionally hide secret instances;
- the editor does not verify semantic coverage against item definitions/mechanics.

A small `World`/`World settings` editor section is preferred over burying this field under an unrelated record type.

New empty worlds should initialize the field to `""`.

Import/export must preserve it exactly apart from ordinary JSON serialization.

Public/private authored worlds must both support the field.

---

# 9. Runtime/install/save behavior

- Generated world data must carry `groundedItemPolicy` unchanged.
- Runtime world bootstrap must copy the current authored policy into runtime world/context access.
- Save migration must take the policy from the **current authored world**, not resurrect stale policy text from an older saved world revision.
- No player action mutates this policy.
- No new save-migration version is required.
- Emergency dumps should naturally include the current policy wherever they already include canonical runtime world/generated world content; no special duplicate diagnostic file is required.

---

# 10. No deterministic narration parsing

Hard rule preserved:

Do not parse free-form narration with regexes, keywords, phrase matching, classifiers, or other deterministic inference in order to decide whether an object was grounded or whether a tracked action occurred.

Grounded category information is supplied to the model prospectively. Canonical state changes still come only from formal engine mechanics.

Narration remains non-authoritative prose.

---

# 11. Character provider routing: throughput

The playtest dumps show Character decisions dominated by generation time on the selected DeepSeek provider. Current request resolution applies:

```text
providerSort = latency
```

to all model roles.

Change routing policy so:

- `modelRole: "character"` resolves with `providerSort: "throughput"`;
- `modelRole: "utility"` remains `latency`;
- `modelRole: "narrator"` remains `latency`;
- same-model provider fallbacks remain enabled;
- model IDs, reasoning budgets, temperature, max tokens, timeout behavior, and fallback model chains remain unchanged.

This applies consistently to Character-role profiles, including ordinary decisions and other Character profiles. Do not hard-pin CoreWeave or another provider in this candidate.

Update current canonical docs that currently state provider routing universally prefers latency.

Add tests asserting role-specific provider sort resolution.

---

# 12. Remove SugarCube back/forward controls

Remove the default SugarCube history back/forward controls from the visible player interface.

Preferred behavior:

- disable/hide SugarCube's UI history navigation controls using the supported SugarCube configuration/UI mechanism;
- do not implement custom back/forward equivalents;
- do not alter Mallowstead's own `framework-history` narrative-history panel;
- do not disable or rewrite SugarCube internal history machinery if persistence/state synchronization still relies on it;
- do not change save/load behavior or asynchronous world-state synchronization.

This is a UI capability removal, not a history-engine refactor.

Add a UI/build regression asserting the back/forward navigation controls are not available to the player.

# 13. Validation and tests

Add/extend tests for at least:

1. authored validator accepts missing, empty, and string `groundedItemPolicy` according to the chosen optional-field rule;
2. non-string values are rejected when present;
3. empty-world/editor defaults include the field;
4. editor import/export round-trips it;
5. generated world data preserves it;
6. runtime world/bootstrap exposes current authored policy;
7. Character decision context includes it exactly once in the intended model-facing location;
8. protocol instructions contain the `grounded != unavailable != narrative prop` invariant;
9. no hidden definitions/instances are automatically enumerated into the policy;
10. old worlds without the field still load;
11. current save migration uses current authored policy;
12. Character role resolves `providerSort=throughput`, Utility/Narrator remain `latency`;
13. SugarCube back/forward player controls are absent while framework narrative history remains present;
14. full existing suites still pass.

Run targeted suites after each implementation stage, then full `test.sh` and `build.sh`, followed by clean-room verification against the exact candidate3 base.

---

# 14. Explicit non-goals

Do not add in this candidate:

- a structured grounded-category ontology;
- automatic matching between prose categories and item definitions/tags;
- `knownTrackedItems` persistent character memory;
- per-character last-known item-state databases;
- secret item-definition enumeration;
- deterministic narration compliance parsing;
- composite tavern workflow actions merely to fix the ale scenario;
- changes to Character reasoning budgets;
- parallel NPC ordinary turns;
- context shrinking/optimization unrelated to the new authored policy;
- broad prompt cleanup/removal of existing safeguards;
- save-schema redesign;
- removal of SugarCube internal history state.

---

# 15. Acceptance criteria

Candidate4 is acceptable when:

1. a world author can write one free-form top-level grounded-item policy;
2. Character decision requests receive that policy as binding authored context;
3. the protocol clearly distinguishes engine-grounded items from free narrative props;
4. a grounded item that is unavailable cannot legitimately be reclassified as a narrative prop merely because no item action is offered;
5. broad authored categories can protect hidden semantic territory without exposing secret item IDs/definitions;
6. no deterministic narration parsing or semantic category validation is introduced;
7. Character requests prefer provider throughput while Utility/Narrator requests preserve latency routing;
8. SugarCube back/forward controls are absent from the player UI without touching internal persistence history;
9. current documentation reflects the new world property and provider-routing policy;
10. targeted, full, build, and clean-room verification pass.
