# Mallowstead 0.1.4 — Transparent Keyed Containers

**Status:** Implementation specification  
**Layer:** Engine + editor  
**Target version:** `0.1.4`

## 1. Purpose

Extend the existing keyed-container mechanic so an authored container may be physically inaccessible while its contents remain canonically visible.

The capability must be generic. No engine behavior may be hard-coded for a medallion, Harlan, a smithy, a display case, or any secret.

## 2. Existing keyed-container rule remains

The existing optional:

```json
{
  "requiredKeyItemId": "specific_key_instance_id"
}
```

continues to control physical access.

The required key is an ordinary transferable item instance and must be directly carried by the acting character.

This patch does not replace or weaken the existing keyed-container access predicate.

## 3. New authored property

A container/sublocation inventory may optionally declare:

```json
{
  "transparent": true
}
```

Default/absent is equivalent to `false`.

`transparent` affects **visibility only**.

It does not grant physical access.

## 4. Visibility and access are separate

For a normal keyed container without the key:

```text
container visible
contents hidden
contents inaccessible
```

For a transparent keyed container without the key:

```text
container visible
contents visible
contents inaccessible
```

For the same transparent keyed container while carrying its required key:

```text
container visible
contents visible
contents accessible normally
```

This separation is the core feature.

## 5. Canonical visibility

When a transparent container is itself within the character's normal grounded visual context, its contents may appear in current-world/view projections even when the character lacks the key.

The view must preserve provenance: visible items should be represented as being **inside/behind the transparent container**, not as loose reachable items.

Visibility must not silently imply possession, reachability, permission, or an executable item action.

## 6. Formal action availability

A character lacking the required key must not receive executable actions against protected contents merely because they are visible.

At minimum this applies to:

- `take_item`;
- `place_item` into the container;
- `transfer_items` extraction/insertion paths;
- `use_item` actions requiring physical access;
- `read_paper`;
- `write_paper`;
- `study_item`;
- `consume`;
- `equip`;
- any equivalent future item manipulation requiring access.

Existing shared physical-access logic remains authoritative.

Visible-but-inaccessible contents may be model context, but not executable options.

## 7. Validation must match options

Manually submitting a formally structured item action that bypasses UI/options must still fail if the actor lacks physical access.

The same shared keyed-container predicate must be used by:

- available-action generation;
- ordinary action validation;
- bulk transfer;
- timelapse item access;
- equivalent item-manipulation paths.

Do not implement transparency by creating a second partial access rule.

## 8. Observation and model context

A transparent container's visible contents should be exposed through the ordinary grounded world/view context.

Models may therefore:

- notice an item;
- mention it;
- reason about it;
- ask about it;
- remember seeing it.

They still cannot formally manipulate it without access.

The engine does not infer any state changes from narration describing attempts to touch, take, inspect, or open the container.

## 9. Editor

The standalone world editor must expose transparency for authored item containers.

When a sublocation has an inventory/container, add a simple author-facing checkbox such as:

```text
Transparent container / contents visible while inaccessible
```

The editor must:

- preserve the field on round trip;
- allow `transparent` together with `requiredKeyItemId`;
- validate it as Boolean when present;
- not require a key merely because `transparent` is true.

The capability should also work for an unkeyed transparent container, even though that usually has no special mechanical consequence.

## 10. Authored validator

Validate:

- `transparent`, if present, is Boolean;
- existing keyed-container references remain valid;
- no story-specific assumptions are introduced.

## 11. Timelapse

Transparency does not change timelapse accessibility.

An actor who can see an item in a transparent keyed container but lacks the required key cannot use that item during timelapse.

Existing direct-key possession semantics remain authoritative.

## 12. Save/migration

The property is authored world data rather than mutable runtime state.

Existing saves remain compatible through current fresh-authoring/runtime-overlay migration rules.

Do not create an `open/closed` state solely for this feature.

## 13. Regression coverage

Add tests covering at least:

1. ordinary unkeyed containers retain current behavior;
2. ordinary keyed containers without a key continue hiding their contents;
3. transparent keyed containers expose contents in grounded view without a key;
4. visible protected contents do not generate `take_item`;
5. manual `take_item` without the key fails;
6. `transfer_items` cannot bypass the key;
7. physical item-use/study/read/write actions cannot bypass the key;
8. carrying the exact required key restores normal access;
9. transferring/dropping the key removes access but not visibility;
10. timelapse cannot use visible protected contents without the key;
11. editor exposes and round-trips `transparent`;
12. validator accepts Boolean transparency and rejects invalid values.

## 14. Non-goals

This patch does not add:

- glass breaking;
- lockpicking;
- container open/close state;
- generic theft law;
- actor-specific ownership permissions;
- special display-case actions;
- story-specific secret behavior;
- automatic narration interpretation.
