# Mallowstead — Intimate Anticipation Update Hardening

**Status:** Implementation specification  
**Layer:** Engine  
**Baseline:** `0.1.4a-medallion`  
**Target version:** `0.1.4b-anticipation`  
**Scope:** Narrow hotfix to intimate anticipation maintenance only

## 1. Problem

An ordinary Character decision may contain both:

- a valid ordinary action / speech / narration response; and
- an update to an already-active intimate context.

Currently, malformed `intimateUpdates.anticipationReplacements` can invalidate the entire Character decision after repair.

Observed failure:

1. Mara had an active `Mara -> player` intimate context with exactly five valid anticipations.
2. The Character response returned a valid ordinary `move` action.
3. The same response attempted to replace the five anticipations.
4. The initial replacement shape did not match the validator contract.
5. Repair transformed it into another invalid shape.
6. The complete Character decision became `invalid_after_repair`.
7. The valid `move` action was therefore lost.

This is incorrect because intimate anticipation maintenance is auxiliary continuation state, not authoritative physical-world execution.

A malformed wishlist must not prevent a character from walking through a door.

## 2. Design rule

Updates to an **already-active intimate context** are best-effort auxiliary state.

If an anticipation update cannot be validated after the existing bounded repair path:

- preserve the previous valid intimate context unchanged;
- preserve the previous five anticipations unchanged;
- discard only the invalid intimate maintenance update;
- continue processing the otherwise-valid Character decision normally;
- record diagnostics.

This is analogous in failure philosophy to weather refresh preserving the previous valid weather state when refresh fails.

The fallback is:

```text
invalid new anticipations
        ↓
discard intimate maintenance update
        ↓
keep previous five
        ↓
ordinary action / speech continues
```

It is **not**:

```text
invalid new anticipations
        ↓
invalidate entire Character decision
```

## 3. Contract synchronization

The Character decision prompt, response schema guidance, validator expectations, and structured repair prompt must all describe the same exact shape for anticipation replacement.

Canonical shape:

```json
{
  "intimateUpdates": {
    "enablePartnerIds": [],
    "disablePartnerIds": [],
    "anticipationReplacements": [
      {
        "partnerId": "player",
        "anticipations": [
          "anticipation 1",
          "anticipation 2",
          "anticipation 3",
          "anticipation 4",
          "anticipation 5"
        ]
      }
    ]
  }
}
```

Requirements:

- `anticipationReplacements` is always an array.
- Every array element is an object.
- Every object contains exactly:
  - `partnerId`
  - `anticipations`
- `partnerId` must identify one of the acting character's currently active intimate partners unless another already-approved transition contract explicitly permits otherwise.
- `anticipations` must contain exactly five valid anticipation strings.
- The model must not return:
  - a partner-id keyed object such as `{ "player": [...] }`;
  - a bare array of five strings;
  - partial patch fragments that the validator cannot apply deterministically.

The repair prompt must include the exact canonical JSON shape rather than merely describing the field semantically.

## 4. Validation layering

Separate validation conceptually into:

### 4.1 Core Character decision

Includes the ordinary turn contract:

- formal action;
- public narrative;
- speech;
- continuation;
- ordinary permitted memory/relationship outputs;
- other authoritative decision fields.

### 4.2 Intimate maintenance payload

Includes updates to already-active intimate anticipations.

An error limited to intimate maintenance must not contaminate a valid core Character decision.

The implementation may achieve this by either:

- validating/sanitizing intimate maintenance separately after the core response has been validated; or
- classifying intimate-maintenance validation failures as recoverable and replacing that subpayload with a no-op.

The important invariant is behavioral, not the internal function layout.

## 5. Repair behavior

Use the existing bounded structured repair path.

For a malformed anticipation replacement:

1. attempt the normal bounded repair;
2. validate the repaired intimate maintenance payload;
3. if valid, apply it normally;
4. if still invalid, discard the intimate maintenance update and preserve previous state.

Do not repeatedly repair without bound.

Do not fabricate default anticipations in engine code.

Do not generate replacement anticipations deterministically.

Do not parse narration to infer what the five entries should have been.

## 6. Atomicity of an active-context replacement

For each already-active directed context:

```text
character -> partner
```

replacement of its five anticipations is atomic.

A replacement either:

- successfully validates as exactly five entries and replaces the old set; or
- fails and leaves the entire old set unchanged.

Never partially apply 1–4 entries.

Never merge malformed replacement output with old entries heuristically.

## 7. Multiple active partners

Failure for one target must not corrupt another target's valid context.

If one response contains multiple `anticipationReplacements`:

- each target-specific replacement should be validated independently where practical;
- a malformed replacement for partner A must not erase partner B's existing state.

If the current response architecture makes per-entry salvage materially more complex, the acceptable narrow fallback for this patch is to reject the whole `anticipationReplacements` collection while preserving all previous intimate contexts.

The patch must not partially corrupt state.

## 8. Diagnostics

When a repaired intimate maintenance update is still invalid, record a diagnostic that is visible in emergency dumps.

Include enough information to determine:

- acting character id;
- affected partner id when recoverable;
- validation failure reason;
- whether repair was attempted;
- that the previous anticipations were preserved;
- that the ordinary Character decision continued.

Do not treat this diagnostic as a fatal AI-decision error.

## 9. No narration parsing

This patch must preserve the Mallowstead architectural rule:

- no regex;
- no keyword matching;
- no phrase parsing;
- no deterministic semantic inference from `publicNarrative` or `spokenText`.

Narration remains non-authoritative prose.

Only validated structured intimate output may change tracked intimate continuation state.

## 10. Initial intimate activation is out of scope

This hotfix does **not** change the behavior of initial intimate-mode activation or the dedicated generation of the first five anticipations.

In particular, this specification does not decide whether failure of the initial Utility → Character anticipation-generation pipeline should or should not be best-effort relative to the ordinary turn.

That behavior requires a separate explicit decision/spec change if desired.

This patch covers only maintenance/replacement of anticipations for an already-active intimate context.

## 11. Regression tests

Add tests covering at least:

### A. Correct replacement

Given:

- an active `A -> B` intimate context with five old anticipations;
- a Character decision with a valid ordinary action;
- a correctly-shaped replacement with exactly five new anticipations;

Then:

- the ordinary action remains valid;
- the five new anticipations replace the old five;
- the context still contains exactly five entries.

### B. Malformed replacement after failed repair

Given:

- an active `A -> B` context with five valid old anticipations;
- a valid ordinary action;
- malformed `anticipationReplacements`;
- repair output that is still invalid;

Then:

- the ordinary action still executes;
- the old five anticipations remain byte-for-byte/semantically unchanged as appropriate to storage;
- no partial replacement is applied;
- a non-fatal diagnostic is recorded.

### C. Repair succeeds

Given malformed initial output but a valid repaired canonical replacement:

- the ordinary action remains valid;
- repaired five anticipations are committed.

### D. Bare string-array shape is rejected safely

A response such as:

```json
{
  "anticipationReplacements": [
    "one",
    "two",
    "three",
    "four",
    "five"
  ]
}
```

must not invalidate an otherwise-valid ordinary turn after fallback.

### E. Partner-keyed object shape is repaired or rejected safely

A response such as:

```json
{
  "anticipationReplacements": {
    "player": ["one", "two", "three", "four", "five"]
  }
}
```

must either be repaired into the canonical schema or discarded without affecting the ordinary action or previous five anticipations.

### F. No partial state corruption

Malformed replacement data must never leave an active context with fewer or more than exactly five anticipations.

### G. Prompt/repair/schema synchronization

Tests should assert that both the Character decision prompt and intimate repair prompt expose the canonical replacement shape expected by the validator.

## 12. Acceptance criteria

The patch is complete when:

1. valid anticipation replacements still work;
2. the Character prompt and repair prompt describe the exact validator-compatible JSON shape;
3. malformed intimate maintenance can no longer invalidate an otherwise-valid ordinary action;
4. failed maintenance preserves the previous five anticipations;
5. no context can be left partially replaced;
6. emergency diagnostics make the fallback visible;
7. no deterministic narration parsing is introduced;
8. initial intimate activation behavior remains unchanged by this patch.
