# Mallowstead — Refactor Pass 1: Structural Cleanup and Local Deduplication

## Status

Implementation specification.

Base: `0.1.4e-candidate1` plus the current-documentation reconciliation patch.

Target product version: `0.1.4e-candidate2` (explicit implementation-version override).

This pass is intentionally behavior-preserving. It removes provably dead code, narrows internal-only surfaces, and consolidates small duplicated implementation paths without changing gameplay rules, model-facing semantics, persistence semantics, authored world data, prompts, or request policy.

Historical versioned specs under `docs/engine/` and `docs/world/` are not normative for this pass. Current repository rules are `AGENTS.md`, `docs/architecture.md`, and `docs/status.md`.

---

# 1. Goals

The first refactor pass has five goals:

1. remove local functions/arguments/exports that are demonstrably unused by the current repository;
2. shrink `setup.GameInternals` to the internal/testing surface that current modules/tests actually consume;
3. consolidate duplicated timelapse-wrapper helpers without changing their current success/failure behavior;
4. centralize duplicated world-state-authority normalization/projection rules used by perception/verbatim memory;
5. reduce duplicated character runtime initialization while preserving the intentional differences between initial materialization and deferred activation.

The pass must make the next, larger `10-game-api.js` module split easier, but does **not** perform that major split yet.

---

# 2. Hard invariants

This pass must not intentionally change observable behavior.

Preserve exactly:

- all public runtime facades (`setup.Game`, `setup.CharacterAPI`, `setup.TimelapseAPI`, etc.);
- formal action availability, validation, execution, event emission, failure codes, and TOCTOU behavior;
- model-facing Character/Utility/Narrator context and prompt text;
- AI JSON parsing/repair/retry behavior;
- `worldStateAuthority` and epistemic provenance semantics;
- world schema and save compatibility;
- authored public/private world content;
- generated world data semantics;
- daytime/nighttime round policy and time transitions;
- trigger/presence/weekly-rhythm behavior;
- transaction snapshot/rollback boundaries;
- current test/debug instrumentation that is actually consumed.

Do not reduce validation frequency, remove world snapshots, parse narration, change prompt/context contents, or optimize model-token usage in this pass.

# 5. Timelapse wrapper helper deduplication

`24-daytime-timelapse.js` and `24-night-timelapse.js` currently duplicate wrapper-level support code, including equivalent time-phase mutation/fallback behavior and final diagnostic recording.

Consolidate only the genuinely shared wrapper mechanics into one common helper surface, preferably owned by `TimelapseCore` or a narrowly named timelapse support module.

At minimum consolidate:

- shared final-result diagnostic recording;
- shared time-phase transition wrapper currently used by day/night wrappers.

The common implementation must preserve the **existing behavior exactly**, including current fallback/rollback behavior if `WorldEnvironment.setTimePhase` is unavailable. Removing that fallback or changing absence of `WorldEnvironment` into a new error is out of scope for this pass.

Local generic `clone()` / `failure()` helpers need not be globally deduplicated merely for line-count reduction unless sharing them clearly simplifies the extracted helper. Do not create a generic catch-all utility module.

Required tests:

- Evening -> nighttime timelapse -> Morning still behaves identically;
- Morning -> daytime timelapse -> Evening still behaves identically;
- failed core/wrapper paths restore/retain the same phase as before;
- diagnostic recording remains non-authoritative and cannot break gameplay;
- existing day/night test suites pass unchanged.

# 6. Centralize world-state-authority mapping

Current authority normalization is duplicated between at least:

- `13-verbatim-memory.js`;
- `14-event-perception.js`.

Create one small shared authority/provenance helper loaded before both consumers. Suggested responsibility:

- normalize allowed authority values:
  - `narrative_only`
  - `grounded_event`
  - `grounded_result`
- map structured observation kinds/events to their current default authority;
- map narrative-input events to `narrative_only`;
- map formal action feedback/results to `grounded_result`;
- map other grounded events to `grounded_event`.

The helper must operate only on already-structured fields. It must never inspect prose content to infer authority or epistemic class.

Do not merge `worldStateAuthority` with epistemic source. They remain orthogonal concepts.

Do not change persisted schema or field names.

Required tests:

- existing event-perception and verbatim-memory authority tests remain byte/structure equivalent where they already assert output;
- mixed narrative + speech projection retains the same authority and epistemic parts;
- explicit valid `worldStateAuthority` still wins over default mapping;
- legacy records without explicit authority retain the same derived result;
- invalid authority values remain rejected/ignored exactly as before according to the current caller contract.

# 7. Consolidate shared character runtime initialization

`installGeneratedData()` and `instantiateDeferredCharacter()` duplicate a substantial block of character materialization logic.

Extract only the **shared normalization/initialization** into one private helper. Suggested responsibility includes current common initialization of:

- `id` / `type`;
- `initialMind` -> runtime Mind v3 structure;
- verbatim/STM arrays and legacy `recentMemories` removal;
- empty runtime `pendingObservations`;
- `recentDialogue`;
- discovery arrays normalization;
- `playerControllable` defaulting;
- mind revision/diagnostics/maintenance fields;
- equipped-items initialization;
- sleeping boolean normalization;
- character inventory creation data shared by both paths, where this can be done without changing ordering or error behavior.

Keep branch-specific policy outside the shared helper:

### Initial world materialization

- respects authored `deferredActivation`;
- inactive deferred characters stay canonical with null placement and `activationState:"inactive"` as today;
- controller assignment semantics remain unchanged;
- all ordinary authored item materialization order remains unchanged.

### Deferred activation materialization

- only materializes authored characters marked `deferredActivation:true`;
- activates at the supplied placement;
- preserves the current controller fallback order;
- materializes only that character's not-yet-materialized authored inventory/equipped items exactly as today;
- preserves discovery of a discovered-required starting location exactly as today.

Do not attempt to redesign activation/presence or item materialization in this pass.

Required tests:

- fresh-world character runtime shape remains unchanged for active characters;
- fresh-world inactive/deferred character shape remains unchanged;
- deferred character activation produces the same fields/controller/placement/inventory/equipment as before;
- duplicate inventory/error behavior remains unchanged;
- public/private generated worlds both pass normal generation/runtime validation;
- save migration tests involving deferred characters remain unchanged.

Where practical, add a focused regression fixture that compares the normalized common fields of fresh and deferred materialization against explicit expected objects rather than relying only on broad end-to-end tests.

# 8. Action metadata consistency check, without registry redesign

The current `ActionRegistry` and `ACTION_AI_METADATA` are parallel structures. A large registry redesign/extraction is deferred to the next pass, but this pass should add a deterministic consistency guard if one does not already exist.

Required invariant:

- every action that requires AI metadata has exactly one metadata entry;
- there are no metadata entries for nonexistent actions;
- attachment of metadata to action definitions remains deterministic.

Do **not** move all metadata into action definitions yet unless it can be done as a trivially mechanical change with no ordering/descriptor differences. The primary requirement of this pass is machine detection of drift, not aesthetic restructuring.

Existing action descriptions/prerequisites must remain byte-for-byte unchanged unless normalization by the current code already changes them.

---

# 9. No major `10-game-api.js` split in Pass 1

Do not perform the large extraction of ActionRegistry, runtime validation, inventory mechanics, or the intent facade in this pass.

Reason: the current file contains significant lexical coupling. First removing dead code, reducing stale `GameInternals` exposure, consolidating materialization, and adding registry consistency checks will make the dependency boundary clearer and reduce the diff/risk of Pass 2.

Pass 2 may then extract large ownership modules through explicit dependency contracts/factories while keeping `setup.Game` / `setup.CharacterAPI` stable.

Because this is intended as implementation-preserving cleanup:

- update the current source/module map in `AGENTS.md`, `docs/architecture.md`, or `docs/status.md` only if this pass actually introduces a new durable module/ownership boundary (for example a shared provenance helper);

# 11. Verification strategy

Run verification incrementally rather than as one final bulk check.

## 11.1 Baseline

Before implementation:

- full `test.sh` must pass;
- full `build.sh` must pass;
- record current source tree and current `setup.GameInternals` key list for comparison.

## 11.2 After dead-code/internal-surface cleanup

- repository-wide symbol search confirms removed local symbols have no references;
- static/internal-surface test passes;
- full relevant unit/domain tests pass.

## 11.3 After each shared-helper extraction

Run the directly affected suites first:

- AI/protocol tests for protocol cleanup;
- perception/memory tests for authority helper;
- day/night/daytime tests for timelapse wrapper helper;
- migration/presence/secrets/core tests for character materialization.

Then run the complete suite.

## 11.4 Final clean-room verification

As with the previous candidate work:

1. produce a patch relative to the agreed `0.1.4e-candidate1 + docs reconciliation` base;
2. apply it to a fresh unpacked copy of that base;
3. require zero patch rejects;
4. run full `test.sh`;
5. run full `build.sh`;
6. verify product version is `0.1.4e-candidate2`;
7. verify no generated/build/archive junk was unintentionally added to source.

# 12. Explicit non-goals

Pass 1 does **not**:

- shrink, redesign, or otherwise change model-facing contexts;
- change prompt wording or model instructions;
- move sponsored-job settlement onto `StructuredAIRequest`;
- strengthen/alter AI option validation behavior;
- change repair counts, retry policy, timeout policy, or provider requests;
- change public/private authored-world parity architecture;
- reduce validation/snapshot frequency;
- change transaction/TOCTOU semantics;
- redesign `ActionRegistry`;
- perform the major `10-game-api.js` module split;
- restructure the large UI module beyond removal of confirmed dead locals;
- reorganize versioned test suites;
- create a generic utility dumping ground;
- alter current gameplay, world content, or save schema beyond the explicit product-version bump to `0.1.4e-candidate2`.

Those belong to later passes and may require separate design discussion.

Refactor Pass 1 is complete when:

7. public facades and model-facing contracts remain unchanged;
8. current project docs remain accurate for any newly introduced ownership boundary;
