# Mallowstead — Small Engine Hardening: Emergency Dumps, Routing Fallbacks, and Mind Reconciliation Contract

**Status:** Implementation specification  
**Layer:** Engine  
**Target version:** `0.1.4c-farmers`

## 1. Purpose

Collect three small engine hardening items discovered during 0.1.4 playtesting:

1. actually compress emergency-dump ZIP archives;
2. make model fallback routing meaningfully escape a failed provider/model route;
3. synchronize the Mind v3 reconciliation output contract so a model/repair response is not rejected for fields the prompt ambiguously permits.

These changes are independent and should remain generic engine capabilities.

## 2. Emergency dump ZIP compression

### 2.1 Current problem

Emergency dumps currently use ZIP `STORE` semantics: files are packaged but not compressed.

Observed playtest dump characteristics were approximately:

- raw ZIP size: ~109 MB;
- the same content with normal DEFLATE: ~17 MB.

Most dump content is highly compressible JSON, including repeated world/history snapshots.

The current behavior therefore wastes substantial disk/upload bandwidth without preserving any extra diagnostic information.

### 2.2 Required change

Emergency dump generation must use ordinary ZIP DEFLATE compression instead of STORE.

Preferred default:

```text
DEFLATE level 6
```

Exact library-specific mapping may vary; use a normal balanced compression setting rather than maximum-compression-at-all-costs.

### 2.3 Data preservation

Compression must be lossless.

Do not remove diagnostic sections merely to reduce size.

This patch does **not** introduce size-triggered deletion, trimming, or history rotation.

The first optimization is compression only.

### 2.4 UI / reliability

Dump generation must remain usable in-browser.

Avoid needless duplicate serialization buffers where the current ZIP library permits streaming/incremental handling.

However, do not introduce a large architectural rewrite solely for memory optimization in this patch.

A temporary short UI pause is preferable to silently dropping diagnostic data.

### 2.5 Regression tests

Add tests or build-time checks where practical that verify:

- emergency dump archive entries use a compressed ZIP method;
- extracted contents are byte-equivalent / JSON-equivalent to the pre-compression payload;
- all expected dump files are still present.

## 3. Model/provider fallback routing

### 3.1 Current problem

`allowProviderFallbacks: true` does not guarantee useful recovery.

If a model is effectively available through only one viable upstream provider, OpenRouter may receive the request successfully but still return a provider-level failure such as:

- 429 rate limit;
- provider unavailable;
- provider timeout;
- shared-pool exhaustion.

In that case retrying the same effective route is not a meaningful fallback.

Observed example:

```text
Narrator primary model
    ↓
NextBit upstream 429
    ↓
no genuinely different provider route
    ↓
weather refresh fails
    ↓
previous weather preserved
```

The local graceful fallback worked, but the routing layer did not expand to a different usable model.

### 3.2 Design goal

Fallback should broaden the route.

Preferred conceptual hierarchy:

```text
configured primary model
    ↓
alternate provider(s) for same model, if OpenRouter has them
    ↓
configured fallback model #1
    ↓
that model's provider fallbacks
    ↓
configured fallback model #2 ...
    ↓
local feature-specific graceful fallback
```

The engine must not hard-code Euryale, NextBit, weather, Character, Utility, or Narrator into the routing mechanism.

### 3.3 Per-role configuration

Character, Utility, and Narrator should be able to define independent fallback model chains.

Conceptually:

```js
models: {
  character: {
    primary: "...",
    fallbacks: ["...", "..."]
  },
  utility: {
    primary: "...",
    fallbacks: ["..."]
  },
  narrator: {
    primary: "...",
    fallbacks: ["..."]
  }
}
```

Exact settings shape should follow current configuration conventions.

Backward compatibility:

- existing single-model settings continue to work;
- no fallback models means current behavior except for diagnostics improvements.

### 3.4 Native OpenRouter routing where possible

Prefer OpenRouter's native model-fallback capability when it accurately expresses the desired ordered chain.

Do not manually issue repeated duplicate requests if a single OpenRouter request can safely carry the ordered fallback model list and still provide useful diagnostics.

If native routing does not expose enough information for current diagnostics/retry behavior, a bounded engine-managed retry may be used.

Keep the number of attempts bounded.

### 3.5 Failure classes

Fallback model routing should be eligible for transient/provider availability failures such as:

- upstream `429`;
- provider unavailable;
- provider timeout;
- equivalent routing/unavailability errors.

Do not automatically fall back to a different model for deterministic contract/schema failures caused by the model's returned JSON unless an existing separate repair/fallback policy explicitly calls for that.

Transport/routing fallback and structured-output repair are separate concerns.

### 3.6 Local graceful fallback remains

Feature-level graceful fallbacks remain authoritative after model routing is exhausted.

Examples:

- weather refresh → preserve previous valid weather;
- optional narration refresh → preserve previous valid state where current architecture already does so.

Do not replace graceful local fallback with infinite model retries.

### 3.7 Diagnostics

Emergency diagnostics should make actual routing behavior visible.

Where available record:

- requested role;
- primary model;
- ordered fallback model list;
- effective model/provider selected by OpenRouter;
- provider/upstream error;
- whether provider fallback was allowed;
- whether a fallback model was attempted/selected;
- final failure reason;
- whether a local graceful fallback was used.

The goal is to avoid future ambiguity such as:

> `allowProviderFallbacks=true`, but did the request actually escape the same unavailable provider?

### 3.8 Regression coverage

Add tests covering:

1. no fallback list preserves backward compatibility;
2. role-specific fallback lists are serialized correctly;
3. transient provider failure can move to a fallback model;
4. deterministic invalid JSON does not automatically trigger transport/model fallback unless separately configured;
5. local graceful fallback still runs after all model routes fail;
6. diagnostics include attempted/selected model/provider information where available.

## 4. Mind v3 reconciliation contract synchronization

### 4.1 Observed problem

A playtest dump produced `INVALID_MODEL_JSON` during Mind v3 reconciliation because Utility returned a `replacementText` field on an outcome for which the validator did not permit `replacementText`.

This indicates a prompt/schema/validator mismatch or insufficiently explicit conditional-field guidance.

This is the same general class of contract drift previously seen with intimate anticipation replacements.

### 4.2 Required behavior

The reconciliation prompt, required response shape, validator, and repair prompt must describe exactly the same conditional schema.

If reconciliation outcomes include variants such as:

```text
keep
replace
merge
drop
...
```

then every outcome must explicitly document:

- required fields;
- optional fields;
- forbidden fields.

Example principle:

```text
outcome = "replace"
    → replacementText required

outcome = "keep"
    → replacementText forbidden

outcome = "drop"
    → replacementText forbidden
```

Use the actual current outcome vocabulary from the existing Mind v3 contract; do not invent new semantic outcomes merely to match this example.

### 4.3 Exact repair guidance

The structured repair prompt must include the same exact outcome-dependent shape as the primary reconciliation prompt.

Do not rely on vague instructions such as "fix the fields".

### 4.4 No semantic weakening

Do not make the validator accept arbitrary extra `replacementText` fields just to silence the error.

The goal is contract synchronization, not permissive schema drift.

If a field is semantically invalid for an outcome, it remains invalid.

### 4.5 Failure semantics

Preserve the existing Mind v3 reconciliation transaction/fallback behavior unless a separate approved spec changes it.

This patch only synchronizes the contract.

Do not introduce new memory semantics.

### 4.6 Regression coverage

Add tests that cover every existing reconciliation outcome and assert:

- the primary prompt describes its exact required/forbidden fields;
- valid examples pass;
- invalid conditional fields fail;
- repair can convert malformed conditional fields into the canonical shape;
- existing reconciliation semantics remain unchanged.

## 5. Architectural invariants

This patch must preserve:

- no deterministic parsing of free-form narration;
- canonical world state remains authoritative;
- model routing failures do not mutate world state;
- repair paths remain bounded;
- getters do not silently repair state;
- diagnostics do not become a second state authority.

## 6. Non-goals

This patch does not:

- rotate/truncate SugarCube history;
- delete old emergency-dump diagnostic data based on archive size;
- add background dump uploads;
- implement automatic online provider discovery outside current OpenRouter capabilities;
- change Character/Utility/Narrator default models by itself;
- make model retries unbounded;
- weaken structured validators;
- redesign Mind v3 memory semantics;
- parse narration to infer protocol compliance.

## 7. Acceptance criteria

The patch is complete when:

1. emergency dump ZIPs are actually DEFLATE-compressed;
2. decompression reproduces the same diagnostic payload;
3. each model role can carry an ordered fallback-model chain;
4. a failed provider route can genuinely escape to a different configured model;
5. routing attempts are visible enough in diagnostics to explain what happened;
6. existing local graceful fallbacks still work;
7. Mind v3 reconciliation prompt/repair/validator agree on conditional fields;
8. existing reconciliation semantics are unchanged;
9. the full regression suite and production build pass.
