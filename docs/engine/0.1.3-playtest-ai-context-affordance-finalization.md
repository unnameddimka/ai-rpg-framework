# Mallowstead 0.1.3 Playtest — AI Context and Affordance Finalization

**Status:** Implementation specification  
**Scope:** AI-facing action availability, human/AI character affordance parity, model-context discipline, playtest product metadata, README accuracy, regression coverage  
**Baseline:** `0.1.2e-candidate3`  
**Target version:** `0.1.3-playtest`  
**Target profile for playtest acceptance:** `public`

---

## 1. Purpose

This is the final engine-side cleanup before the public-world playtest.

The patch should reduce avoidable model confusion rather than add new mechanics. In particular, the Character model must not be shown formal actions that cannot currently be executed, while the broader repair/mechanics context must remain capable of exposing relevant mechanics whose prerequisites are not yet satisfied.

The patch also records two project-level design guidelines for future work:

1. keep model-facing context as small and decision-relevant as practical;
2. preserve ordinary human/AI character-action parity, subject to intentional character-specific capabilities and limitations.

These are design guidelines, not absolute invariants. They should guide future context and action-contract changes without forcing artificial symmetry or deletion of information required for correctness, grounding, validation, safety, or a model's assigned role.

## 3. Model-context minimality guideline

Add the following project-level guideline to the canonical architecture/repository guidance in suitable wording:

> Model-facing context should be kept as small, relevant, and role-appropriate as practical. For an ordinary Character decision, prefer including information that helps the model understand the current situation, make a human-like character decision, or execute an available operation. Information that serves none of those purposes should preferably be omitted.

The phrase **human-like character decision** is intentional. Character context is not merely an API-operability prompt: personality, current social situation, grounded observations, relevant memories/beliefs, and other character-level information may be necessary even when they are not direct action parameters.

### 3.1 Role-specific application

The same general discipline applies to other model roles, but according to their task:

- **Character:** situation understanding + human-like character decision + executable operations;
- **Utility / repair / maintenance:** only the grounded data needed to perform that bounded utility task;
- **Narrator:** only the committed grounded material needed for the requested presentation work.

Do not interpret the guideline as requiring all roles to receive the same projection.

### 3.2 This is not a hard minimization invariant

Do not remove context merely because it is not obviously used in one successful example.

Context required for any of the following remains legitimate:

- deterministic contract interpretation;
- grounding and epistemic safety;
- validation or repair;
- character identity/personality;
- relevant mind/retrieval state;
- task-specific Utility/Narrator work;
- preventing a known class of invalid or hallucinated behavior.

The goal is **signal over noise**, not smallest possible token count at any cost.

### 3.3 Avoid duplicate or dead capability context

Existing architectural rules against duplicating large data under aliases remain in force.

In addition, do not expose action records that are impossible to invoke in the current state merely to advertise that the engine knows such an action type exists. Executable capability advertisement belongs in `view.available_actions`; broader mechanic awareness belongs in `relevantMechanics`.

## 4. Human / AI character affordance parity guideline

Add a neighboring project-level guideline:

> An AI-controlled character should generally be able to express the same ordinary in-world actions that the same character could perform under Human control in the same canonical situation, subject to that character's authored capabilities and limitations.

This is **per-character parity**, not universal character homogenization.

### 4.1 Character-specific capabilities are intentional

Mara's unique abilities, Chuhaister's unique abilities, and any future character-specific abilities are intentional authored differences.

A character who does not own such an ability must not receive it merely for parity. Conversely, when a character does own a currently usable authored ability, AI control must not lose access to it merely because the ability is unusual or character-specific.

Likewise, authored restrictions, equipment, knowledge, physical situation, locks, inventory, location, presence, and other canonical differences may legitimately produce different available actions for different characters.

### 4.2 Controller-role differences must be intentional

The guideline is aspirational rather than a claim that every controller-level workflow is symmetric today.

Operations that are not ordinary character actions — settings, save/load, debug/admin UI, controller switching, presentation controls, etc. — are outside this parity rule.

If an in-world mechanic intentionally depends on the Human/AI controller role, that difference should remain explicit rather than emerging accidentally from separate UI/model implementations.

### 4.3 One deterministic capability truth

Do not implement parity by making the AI inspect DOM controls or by maintaining a second hand-written AI-only capability list.

The deterministic engine action contract remains authoritative. Human controls and AI exposure should derive from the same canonical action availability/options wherever practical.

## 5. `view.available_actions` must be executable-now

The existing architecture already defines:

```text
view.available_actions = executable-now formal-action contract
```

Make the implementation actually satisfy that contract.

### 5.1 Current defect

The current base-action grant path grants every `BASE_ACTION_TYPES` action before checking whether its current option domain permits any invocation.

This can expose records such as:

- `move_within_location` with no destination;
- `take_item` with no item;
- `drop_item` with no owned item;
- `give_item` without both an owned item and a reachable target;
- `give_money` with a reachable target but no positive transferable amount.

Such records are noise in Character context and contradict the prompt's statement that `AVAILABLE ACTIONS RIGHT NOW` contains only currently possible actions.

### 5.2 Required availability semantics

An action may appear in `view.available_actions` only when, in the current canonical state, the actor can construct at least one invocation that can pass that action's current deterministic prerequisite/options contract, assuming any required free-form input is supplied validly.

For the current base actions this means at minimum:

- `move`: at least one current `destination_id`;
- `move_within_location`: at least one current `destination_id`;
- `take_item`: at least one current `item_id`;
- `drop_item`: at least one current `item_id`;
- `give_item`: at least one current owned `item_id` **and** at least one current reachable `target_id`;
- `give_money`: at least one current reachable `target_id` **and** `maximum_amount > 0`.

The implementation may centralize this as action-specific availability logic rather than hard-coding these checks at the final serialization site, but the observable contract above is required.

### 5.3 Free-form parameters

Do not incorrectly hide actions merely because a valid invocation still needs model/player-authored free-form input.

Examples:

- `write_paper` may require content text supplied at execution time;
- an item-specific use action may require a bounded/free-form input field;
- `give_money` requires an amount chosen at execution time, but it is available only if the current upper bound permits some positive amount.

The question is whether **some valid invocation is currently possible**, not whether every final parameter value has already been chosen.

### 5.4 Non-base actions

Existing source/prerequisite gating for non-base actions should remain authoritative.

Where an existing non-base grant can still produce an action record with no executable option, harden it consistently rather than preserving an empty record for historical reasons.

Do not remove a valid zero-input action merely because it has no option arrays; if its deterministic prerequisites are currently satisfied, it is executable and should remain available.

## 6. Player controls and `available_actions` must agree

Use the Human action UI as the behavioral reference for what “available now” means, while keeping the engine — not the DOM — as the source of truth.

### 6.1 Enabled-control parity

For an ordinary formal character action:

- if the player could select the control and construct a valid action now, the corresponding action should be present in `view.available_actions` for that same character/state;
- if no valid invocation exists now, the Character model must not receive that action in `view.available_actions`;
- the Human UI must not present the same action as selectable/enabled when the engine says it has no executable invocation.

The UI may continue to render disabled placeholders for discoverability. Disabled UI is not capability advertisement to the model.

### 6.2 Fix UI drift exposed by the cleanup

Audit the formal-action panel for predicates that were previously inferred indirectly from another action's options or from visible world data.

In particular, money transfer must not become selectable merely because a reachable character exists when the actor has no positive amount of gold to transfer.

Prefer checking the corresponding `view.available_actions` record/options directly instead of recreating a weaker UI-only predicate.

### 6.3 No new action system

Do not introduce a second action registry, UI capability registry, or AI capability registry.

This patch should tighten the existing `CharacterAPI` / `ActionRegistry` contract.

## 7. Keep `relevantMechanics` broader than `available_actions`

Do **not** apply the executable-now filter to `relevantMechanics`.

The two projections intentionally answer different questions:

- `view.available_actions`: **what can I execute right now?**
- `relevantMechanics`: **what grounded mechanic is relevant here, including mechanics that may need a prerequisite first?**

The existing relaxed-source gating used for action-contract repair must remain capable of exposing an anchored mechanic even when one or more executable prerequisites are missing.

Example shape:

- an item or environmental source can make a mechanic relevant;
- the final action may still be absent from `available_actions` because the actor lacks a tool, target, free slot, key, reachable destination, etc.;
- the Character model/repair pass can then look for an available prerequisite action rather than hallucinating completion.

Do not collapse the two mechanisms into one list.

## 8. AI prompt / protocol expectations

The current Character protocol language already distinguishes:

- `RELEVANT ENGINE MECHANICS`;
- `AVAILABLE ACTIONS RIGHT NOW`.

Preserve that distinction.

No broad prompt rewrite is required unless necessary to keep the wording truthful after the implementation change.

Do not add extra explanatory capability text to compensate for keeping impossible actions in context; the impossible actions should simply be absent.

## 9. README commerce wording

Update the root README so it no longer claims that no buy/sell or price system exists at all.

Current reality is narrower:

- the world has the Maksym merchant loop;
- selected goods have explicit external-sale values used by that loop;
- characters negotiate through dialogue and complete the exchange using grounded item transfer and gold transfer;
- there is still no universal village economy/price model;
- there is still no dedicated atomic `Trade`/shop action that commits the whole negotiated deal at once.

State that accurately and compactly.

### 9.1 Economy stabilization is deferred

Do not rebalance prices, introduce shared market-price knowledge, add a general economy layer, or create a new Trade action in `0.1.3-playtest`.

Economy/price stabilization belongs to the next version after playtest feedback.

## 11. Tests

Add regression coverage for the executable-now contract.

At minimum cover:

1. a base action with an empty option domain is absent from `view.available_actions`;
2. `move_within_location` is absent when no internal destination is possible and present when one is possible;
3. `take_item` is absent with no takeable item and present when a valid item exists;
4. `drop_item` is absent with no owned item and present when a valid owned item exists;
5. `give_item` requires both at least one owned item and at least one reachable target;
6. `give_money` is absent when `maximum_amount <= 0`, even if a reachable target exists;
7. `give_money` is present when a reachable target exists and some positive amount is transferable;
8. a valid zero-input action remains exposed when its prerequisites are satisfied;
9. `relevantMechanics` can still contain a grounded mechanic that is absent from `available_actions` because an executable prerequisite is missing;
10. ordinary controller-neutral character actions do not gain/lose availability merely because the same character/state is viewed under Human versus AI control;
11. authored character-specific abilities remain character-specific rather than being granted universally;
12. the Human UI does not expose an enabled formal-action control for an action that has no executable invocation.

Existing action-contract repair, AI, UI, hardening, migration, timelapse, weekly merchant, secrets, and release-profile suites must continue to pass.

## 14. Acceptance Criteria

The engine side of `0.1.3-playtest` is complete when:

1. Product version is `0.1.3-playtest` through the existing authoritative version source.
2. `view.available_actions` contains only actions for which at least one valid current invocation exists, including correct handling of current base-action option domains and positive money-transfer bounds.
3. The Human formal-action UI cannot enable an action that the canonical action contract says has no executable invocation.
4. `relevantMechanics` remains intentionally broader and can expose grounded-but-not-yet-executable mechanics for prerequisite planning/repair.
5. Ordinary Human/AI character affordances derive from the same deterministic action truth; character-specific authored abilities remain specific to their owners.
6. Canonical project guidance records both the model-context minimality guideline and the human/AI character affordance parity guideline.
7. Root README accurately describes the current narrow merchant/price loop without claiming a universal economy or atomic Trade action.
8. No new economy balancing or Price-specific work is introduced.
9. Public-profile regression tests pass, along with the full existing relevant test suite.
