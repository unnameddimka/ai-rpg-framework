# Mallowstead — Intimate Motivation v2 and Cognitive-State Hardening

**Status:** Implementation specification  
**Layer:** Engine  
**Baseline:** `0.1.4c-farmers`  
**Target version:** `0.1.4d-cognitive`

## 1. Purpose

This patch combines four related improvements discovered during long-form playtesting:

1. replace the flat five-item intimate anticipation list with a more structured motivational model that preserves initiative and imagined future scenes;
2. add safe, periodic balanced consolidation of the full belief space using semantic clustering;
3. harden relationship summaries so durable current relationship facts do not lag behind memory;
4. finish synchronization of Mind v3 reconciliation and tighten belief induction so episodic/transient facts do not unnecessarily accumulate as beliefs.

The patch must preserve the core Mallowstead architecture:

- free-form narration is non-authoritative;
- the engine does not deterministically parse prose;
- semantic judgments belong to models;
- canonical state changes occur only through validated structured contracts;
- auxiliary cognitive-state failures must not corrupt ordinary gameplay.

---

# Part I — Intimate Motivation v2

## 2. Scope and design principle

The engine continues to contain **no explicit sexual/18+ action vocabulary or mechanics**.

There are no formal engine actions for sexual behavior, body simulation, arousal, intercourse, consent meters, sexual positions, or equivalent explicit mechanics.

Intimate mode is only a lightweight, private motivational continuation state for adult characters during close romantic/intimate scenes.

Ordinary narration/dialogue remains capable of expressing a wide range of fictional behavior, but the engine does not model explicit sexual acts as tracked mechanics.

## 3. Adult-only eligibility

Intimate mode is available only when **both actor and target are authored as adults**.

The engine must validate both sides structurally.

If either character is a minor or is not eligible under the current adult-character metadata:

- intimate activation is invalid;
- no intimate context is created;
- no intimate anticipation-generation request is sent for that pair.

Do not infer adulthood from prose, appearance, occupation, relationship, or dialogue.

Use canonical authored character metadata only.

## 4. Directed per-partner state

Intimate contexts remain directional and per partner.

Examples:

```text
Mara -> Traveler
Traveler -> Mara
Mara -> Nell
```

are independent states.

A character may have multiple active partner contexts at once.

No automatic symmetry is introduced.

## 5. New canonical intimate motivation shape

Replace the old flat five-entry anticipation list with exactly:

```js
{
  impulse: "...",
  imaginedMoments: [
    "...",
    "..."
  ],
  openAnticipations: [
    "...",
    "..."
  ]
}
```

Every active directed intimate context must contain:

- exactly **1 `impulse`**;
- exactly **2 `imaginedMoments`**;
- exactly **2 `openAnticipations`**.

This preserves five motivational elements total while giving them explicit semantic roles.

## 6. `impulse`

`impulse` is the character-owned proactive drive for the near development of the scene.

It should describe something the character personally wants to:

- do;
- initiate;
- cause;
- try;
- steer toward;
- make happen.

It should not merely restate what the character hopes the partner will do.

It should not be a multi-step action queue.

It should not be a formal engine plan.

Example semantics:

```text
She wants to keep him uncertain for a little longer and choose the next turn herself.
```

The purpose of `impulse` is to preserve character initiative without adding a generic "be proactive" instruction to all Character behavior.

## 7. `imaginedMoments`

`imaginedMoments` contains exactly two anticipated scene-images the character currently wants to realize or move toward.

Each entry is an imagined possible moment rather than a guaranteed future fact.

It may include:

- self;
- partner;
- posture or spatial relation;
- words;
- atmosphere;
- emotional tone;
- an expected reaction;
- an imagined sensation;
- a desired social/romantic moment.

These are private mental projections.

They are not:

- canonical future state;
- deterministic goals;
- formal action sequences;
- promises that the scene must reach them.

The Character model may:

- move toward one;
- reinterpret one;
- abandon one;
- judge that reality became close enough to it;
- replace it with a new imagined moment.

The engine never compares narration to these moments deterministically.

## 8. `openAnticipations`

`openAnticipations` contains exactly two free-form motivational anticipations.

They may be:

- something the character hopes to receive;
- something the character wants to feel;
- something the character wants to discover;
- curiosity about the partner;
- an emotional result;
- another proactive desire;
- another imagined scene;
- another scene-specific concern.

No additional semantic category is imposed.

This field intentionally leaves room for emergent variation.

## 9. Generation contract

Initial generation for a newly activated adult `character -> partner` intimate context must return the exact canonical shape.

The generation prompt must explain the semantic distinction among:

- `impulse`;
- `imaginedMoments`;
- `openAnticipations`.

It must discourage semantic collapse such as five variations of:

```text
deepen trust
feel closer
strengthen the bond
feel safe
feel connected
```

The generator should prefer concrete, scene-relevant content while preserving character personality and current context.

Do not impose a predetermined sexual script.

## 10. Replacement/update semantics

Maintenance of an already-active intimate context replaces the **entire motivation block atomically**.

Canonical replacement object:

```json
{
  "partnerId": "player",
  "motivation": {
    "impulse": "...",
    "imaginedMoments": ["...", "..."],
    "openAnticipations": ["...", "..."]
  }
}
```

The exact outer field naming may follow current `intimateUpdates` conventions, but prompt, validator, repair, and executor must agree on one exact shape.

Do not independently patch individual strings.

A successful replacement changes the whole block.

A failed replacement changes none of it.

## 11. Avoid semantic degeneration on replacement

Replacement guidance must explicitly state:

> Do not merely generalize fulfilled concrete anticipations into vaguer versions of the same desire. When the scene develops, create new concrete possibilities that move the character's private imagination or initiative forward.

Examples of undesirable degeneration:

```text
concrete desired moment
→ deepen trust
→ deepen connection
→ feel safe together
→ ask what the partner wants
```

The goal is not novelty for its own sake, but preventing a concrete motivational state from collapsing into generic relational abstractions.

## 12. Best-effort maintenance fallback

Existing `0.1.4b` best-effort behavior remains.

For an already-active intimate context:

1. attempt normal validation;
2. use the existing bounded structured repair path;
3. if the repaired replacement is valid, commit it;
4. if it is still invalid:
   - discard only that intimate maintenance replacement;
   - preserve the previous complete motivation block;
   - continue the otherwise-valid Character decision;
   - record a non-fatal diagnostic.

Do not fabricate replacement content in engine code.

Do not partially apply fields.

## 13. Legacy save migration

Old saves may contain the previous flat five-anticipation intimate structure.

Do not attempt deterministic or heuristic semantic conversion.

On migration:

- discard legacy active intimate contexts;
- initialize the current intimate context store empty;
- preserve memories, relationships, beliefs, and all ordinary character/world state.

This is acceptable because intimate context is transient encounter continuation state rather than autobiographical memory.

## 14. Timelapse

Any successful Day or Night timelapse continues to clear all active intimate contexts.

Rollback semantics remain unchanged:

- if timelapse fails transactionally and the old world is restored, old intimate state is restored with it;
- after a successful coarse-time transition, intimate state is gone.

# Part II — Balanced Belief Consolidation

## 15. Keep ordinary reconciliation

The existing small salient-belief reconciliation mechanism remains.

It continues to handle current cognitive pressure such as:

- contradictions;
- fresh evidence;
- newly salient beliefs;
- local revise/contextualize/supersede/remove decisions.

Do not replace it with large-scale consolidation.

Balanced consolidation is a separate periodic housekeeping pass.

## 16. When balanced consolidation runs

Balanced belief consolidation is eligible during **Night timelapse maintenance**.

It should run at most once per character per Night.

It is intentionally absent from ordinary turns and Day timelapse unless a later spec changes that.

## 17. Clustering preflight

The first stage is a Utility semantic-clustering request.

The request receives the character's current belief catalog.

All current beliefs are eligible for clustering unless excluded by basic structural validity.

Do not restrict clustering to low-activation beliefs.

Activation may be included as context, but it does not determine eligibility.

The preflight must return only groups of existing belief IDs.

Conceptual shape:

```json
{
  "clusters": [
    {
      "beliefIds": ["b1", "b7", "b19", "b22", "b31"]
    },
    {
      "beliefIds": ["b4", "b8"]
    }
  ]
}
```

The clustering request does **not** rewrite beliefs.

## 18. Narrow semantic cluster definition

Prompt guidance must define a cluster narrowly:

> Group beliefs together only when they belong to the same sufficiently narrow semantic theme and could reasonably be reviewed together for redundancy, merging, revision, or removal without collapsing distinct meanings.

Bad cluster:

```text
everything about Dmytro
```

Good clusters may resemble:

```text
Dmytro as creator / architect
cohabitation and domestic status with Dmytro
romantic trust with Dmytro
sexual/romantic interaction style
Mara's relation to villagers' fear
Nell as trusted friend
world mechanics and causality
```

The actual clusters remain model-generated.

The engine must not infer semantic clusters deterministically.

## 19. Cluster validation

The engine validates only structure and IDs.

At minimum:

- every listed ID exists;
- no invented IDs;
- a belief appears in at most one returned cluster;
- duplicate IDs are invalid;
- empty clusters are invalid;
- singleton clusters may be accepted structurally but are not eligible for balanced consolidation;
- beliefs may remain unclustered.

Malformed clustering output follows the existing bounded repair pattern.

If clustering still fails after repair:

- skip balanced consolidation for that character for this Night;
- preserve all beliefs;
- record diagnostics.

## 20. Minimum cluster threshold

After successful clustering, find the largest cluster.

Balanced consolidation runs only if the largest cluster contains at least:

```text
5 beliefs
```

If every cluster contains fewer than five beliefs:

- do not issue the second consolidation model request;
- do not mutate beliefs;
- finish housekeeping for that character.

This threshold prevents wasting a second model request when there is too little semantic density to justify consolidation.

## 21. Choosing the cluster

Choose exactly **one largest eligible cluster** per character per Night.

If several clusters tie for largest size, use a stable engine-owned tie-breaker such as:

- oldest minimum `lastConsolidatedAt`;
- otherwise deterministic ID ordering.

Do not ask another model merely to break ties.

## 22. `lastConsolidatedAt`

Beliefs may carry engine-owned housekeeping metadata such as:

```js
lastConsolidatedAt
```

This field records when the belief most recently participated in a successful balanced consolidation review.

It is housekeeping metadata only.

It must not:

- raise activation;
- lower activation;
- imply that the character consciously thought about the belief;
- become evidence;
- appear as autobiographical memory.

For newly created beliefs the field may be absent/null until first review.

## 23. Balanced consolidation request

The second Utility request receives the full selected cluster.

Its task is:

> Preserve every distinct durable meaning represented in the cluster. Remove material that is not truly a durable belief, eliminate redundancy, and merge or revise beliefs only when the resulting belief faithfully preserves the relevant durable meaning.

The request must not be given a target output count.

Do not say:

```text
reduce 20 beliefs to 5
```

The resulting number is an emergent consequence of semantic consolidation.

## 24. Consolidation operations

The consolidation result must support the semantic equivalents of:

```text
KEEP
REMOVE_AS_NON_BELIEF
MERGE
REVISE
```

Exact naming may match current Mind v3 conventions where possible.

Conceptual output:

```json
{
  "results": [
    {
      "operation": "keep",
      "sourceBeliefIds": ["b1"]
    },
    {
      "operation": "remove_as_non_belief",
      "sourceBeliefIds": ["b2"]
    },
    {
      "operation": "merge",
      "sourceBeliefIds": ["b3", "b4", "b5"],
      "replacementText": "..."
    },
    {
      "operation": "revise",
      "sourceBeliefIds": ["b6"],
      "replacementText": "..."
    }
  ]
}
```

## 25. Provenance and coverage invariants

Every belief in the selected source cluster must be accounted for exactly once.

For a cluster of:

```text
[b1, b2, b3, b4]
```

the validated result must cover all four IDs exactly once across all operations.

No source belief may be:

- omitted;
- duplicated;
- used by multiple operations.

No outside belief ID may appear.

`MERGE` requires at least two source beliefs.

`REVISE` applies to exactly one source belief unless the existing contract deliberately defines otherwise.

## 26. Atomicity

Balanced consolidation is atomic at the selected-cluster level.

If:

- primary output is invalid;
- repair is attempted;
- repaired output remains invalid;

then:

- none of the selected cluster changes;
- no partial merge/remove/revise is applied;
- all original beliefs remain;
- diagnostics record the failed maintenance pass.

Do not salvage individual operations from an invalid cluster result.

## 27. Confidence and activation

Do not invent simplistic deterministic confidence arithmetic solely for consolidation.

Reuse current Mind v3 semantics where applicable.

At minimum:

- `KEEP` preserves current belief confidence/content;
- housekeeping review itself does not increase activation;
- merged/revised beliefs must receive confidence/metadata according to one explicit engine contract;
- do not let the model silently invent arbitrary activation values unless that is already an approved Mind v3 mechanism.

The implementation spec should document the exact chosen confidence handling before code is committed if current infrastructure does not already define it.

## 28. What should be removed as non-belief

Balanced consolidation should be explicitly reminded that beliefs are durable interpretations, not event storage.

Candidates for `REMOVE_AS_NON_BELIEF` include entries whose semantic content is primarily:

- a completed event;
- a temporary scene state;
- a current plan that has already ended;
- a one-off physical fact;
- a transient location;
- a completed action;
- information whose durable significance is already represented by memory and does not constitute a standing interpretation.

Example:

```text
"Dimka promised this morning to build a well by evening."
```

is primarily event memory.

A durable belief derived from it might instead be:

```text
"Dimka tends to keep even extraordinary promises when he gives his word."
```

The engine does not make this distinction with text rules; Utility does.

# Part III — Belief Induction Hardening

## 29. Tighten belief induction

The belief-induction prompt should more strongly distinguish:

```text
experienced event
```

from:

```text
durable interpretation of experience
```

Do not create a belief merely because something happened.

Do not normally create beliefs that are only:

- a chronological event;
- a current plan;
- a completed action;
- a temporary world state;
- a transient physical condition;
- a scene-specific intention.

A new belief should remain useful as an interpretation beyond the originating scene.

## 30. Examples

Prefer:

```text
Dmytro tends to keep promises even when they sound impossible.
```

over:

```text
Dmytro promised to build a well by evening.
```

Prefer:

```text
Nell trusts her own judgment of people more than village superstition.
```

over:

```text
Nell said she was not afraid of the new well.
```

Prefer:

```text
Harlan respects people who prove themselves through dependable work.
```

over:

```text
Harlan paid Dmytro five gold after today's work.
```

These examples are semantic guidance only.

Do not implement deterministic matching against them.

# Part IV — Relationship Summary Hardening

## 31. Relationship summary semantics

A relationship summary must be a **self-contained current summary of all durable facts that materially define this character's present relationship with the target person**.

It is not merely an emotional adjective and it is not a chronological event log.

## 32. What belongs in a relationship summary

Where currently durable and relevant, summaries should include:

- present relationship type/status:
  - acquaintance;
  - friend;
  - lover;
  - spouse;
  - employer;
  - dependent;
  - rival;
  - etc.;
- durable trust/fear/resentment/affection;
- current standing arrangements:
  - lives with me;
  - works for me;
  - is staying in my home;
  - has an ongoing invitation;
  - owes/holds an enduring obligation;
- important standing boundaries:
  - romance is not expected;
  - secrecy has been promised;
  - the person is not trusted with a particular responsibility;
- durable social commitments that materially shape future interaction.

## 33. What does not belong

Do not turn relationship summaries into event histories.

Avoid accumulating:

```text
then we drank
then he gave me a chain
then we walked to the well
then we ate breakfast
```

Those belong in memory.

The summary should state the current durable relationship meaning resulting from such events.

## 34. Upsert criterion

The Character model should return a relationship upsert when either:

1. the emotional/social relationship materially changes; or
2. a durable standing fact that defines the relationship materially changes.

Examples:

```text
acquaintance -> friend
friend -> close friend
lover -> lover who now lives with me
friendly traveler -> trusted friend
ordinary friend -> friend who has promised to keep my secret
```

The engine still does not parse narration to determine these changes.

The Character model semantically judges them and returns structured `relationshipsToUpsert`.

## 35. No separate relationship maintenance model call

Do not add a new periodic relationship-summary model request in this patch.

The stricter ordinary Character contract should allow relationship summaries to converge naturally as meaningful interactions continue.

# Part V — Mind v3 Reconciliation Contract Completion

## 36. Finish `replacementText` synchronization

The existing reconciliation bug must be fixed completely.

Observed issue:

- prompt/repair instructed Utility to return `replacementText` for `contextualize`;
- Utility complied;
- validator still rejected the field.

The primary prompt, required response shape, validator, repair prompt, and executor must all use the same outcome-dependent contract.

## 37. Outcome-specific fields

For every existing reconciliation outcome, explicitly define:

- required fields;
- optional fields;
- forbidden fields.

If `contextualize` semantically requires `replacementText`, the validator must permit/require it.

If another outcome forbids it, repair and prompt must forbid it too.

Do not weaken the validator to accept meaningless fields universally.

## 38. Preserve existing reconciliation semantics

This patch does not redesign ordinary reconciliation.

It only completes contract synchronization and preserves its current transaction behavior.

# Part VI — Diagnostics and Safety

## 39. Diagnostics

Emergency dumps should expose enough information to debug:

### Intimate v2
- acting character;
- partner;
- previous motivation block;
- attempted replacement;
- validation/repair failure;
- whether old block was preserved.

### Balanced belief consolidation
- character;
- cluster sizes returned by preflight;
- selected cluster IDs;
- whether threshold `< 5` skipped the second call;
- consolidation result;
- repair status;
- atomic commit/fallback result.

### Relationship updates
Existing AI exchange logs should remain sufficient; no second relationship authority is created.

## 40. No deterministic narration parsing

This patch must not add:

- regex over narration;
- keyword matching;
- phrase detectors;
- deterministic inference of intimacy;
- deterministic fulfillment detection;
- deterministic relationship-status extraction;
- deterministic belief clustering;
- deterministic identification of episodic versus durable semantic content.

Models perform semantic interpretation and return structured state.

The engine validates structure, IDs, eligibility, atomicity, and canonical-state invariants.

2. clustering may return multiple narrow clusters;
3. unknown IDs fail validation;

## 45. Reconciliation contract tests

Cover every current reconciliation outcome.

# Part VIII — Non-goals

## 46. This patch does not add

- explicit sexual engine actions;
- sexual body simulation;
- arousal systems;
- consent meters;
- deterministic sexual progression;
- intimate mode for minors;
- deterministic narration analysis;
- a target belief count;
- automatic deletion based solely on low activation;
- a hard maximum number of beliefs;
- full-mind rewriting in one transaction;
- more than one balanced cluster consolidation per character per Night;
- a separate relationship-maintenance model request;
- new autobiographical memory semantics.

# Part IX — Acceptance Criteria

The patch is complete when:

1. intimate motivation uses the exact `1 impulse + 2 imagined moments + 2 open anticipations` structure;
2. intimate mode is structurally unavailable unless both participants are adults;
3. failed intimate maintenance preserves prior valid motivation and does not cancel ordinary actions;
4. legacy active intimate contexts are safely cleared on migration;
5. ordinary salient reconciliation remains;
6. Night maintenance performs semantic clustering of the full belief catalog;
7. no second consolidation request is made when every cluster has fewer than five beliefs;
8. exactly one largest eligible cluster may be balanced-consolidated per character per Night;
9. balanced consolidation preserves all distinct durable meanings without a target output count;
10. invalid consolidation never partially mutates a cluster;
11. belief induction is stricter about event-vs-belief semantics;
12. relationship summaries capture durable current status and standing arrangements;
13. reconciliation `replacementText` contract is fully synchronized;
14. no deterministic prose parsing is introduced;
15. full regression suite and production build pass.
