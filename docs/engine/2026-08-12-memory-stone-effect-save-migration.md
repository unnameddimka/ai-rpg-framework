# Generic Memory-Count Item Effect and Save Migration

## Goal

Implement a deterministic generic item-use effect that reports the acting character's short-term and long-term memory entry counts as private grounded feedback, and verify that newly authored stable instances such as the Memory Stone enter older compatible saves through the existing transactional authoring reconciliation.

## Generic authored item use

Item definitions may declare one optional `useAction` containing authored configuration only:

- `actionLabel` — player/model-facing interaction label;
- `effectId` — identifier of an engine-owned allowlisted deterministic effect;
- `publicText` — grounded public physical-action template;
- `feedbackText` — private grounded feedback template interpreted only by the selected effect.

World data never contains JavaScript or arbitrary executable effect scripts.

An owned item with a valid `useAction` grants the ordinary formal action `use_item` through the same `ActionRegistry` / `view.available_actions` path used by both HumanController and AIController.

`use_item` accepts the concrete owned `item_id`. Only item IDs currently offered by the canonical view are valid choices.

## `report_memory_counts`

Add the allowlisted engine effect:

`report_memory_counts`

When executed, read the acting character's canonical mind immediately before the resulting private feedback observation is enqueued.

Report only:

- `recentMemories.length` as **Short-term memory**;
- `longTermMemories.length` as **Long-term memory**.

Do not report token counts, byte/character sizes, context-window usage, capacity, percentages, thresholds, or qualitative health/overload judgments.

The observation generated by this action is not included in the reported counts. Existing observation/memory processing may occur normally afterward.

## Public physical action

A successful `use_item` emits the authored grounded public physical-action event in the actor's current location.

Nearby perceivers may observe the physical action according to normal event/perception rules.

The public event must not contain either memory count.

## Private result

The effect returns one grounded private feedback entry addressed only to the acting character.

The user/model-facing text must be natural prose, for example:

> The stone grows faintly warm in your hand. Short-term memory: 17 entries. Long-term memory: 83 entries.

Do not duplicate the numerical counts into a public event. The private structured feedback metadata may identify the item/effect but should not redundantly expose the counts as debug-style fields when the prose already carries them.

## Controller independence

Private feedback belongs to the character rather than its current controller.

- Under HumanController, the ordinary player-facing private-feedback UI displays the observation.
- Under AIController, the same feedback is routed into that character's normal pending-observation / AI-context path.

The engine effect does not branch semantically by controller type.

## Read-only semantics

`report_memory_counts` does not directly modify memories, beliefs, relationships, continuation, psychology, item state, charges, cooldowns, or any other objective state.

The ordinary consequences of taking a formal action and later interpreting/remembering observations remain unchanged.

## Save migration / authored instance reconciliation

Use the existing transactional migration model: **fresh current authored world + preserved saved lives**.

The fresh candidate already contains every current authored starting item instance. Saved item instances are then overlaid by stable item-instance ID.

Therefore:

- if a current authored stable instance ID is completely absent from the old save, the fresh authored instance remains at its authored initial placement;
- if that stable ID already exists in the save, the saved runtime instance replaces the fresh starting instance and preserves its valid saved placement/state;
- repeated save/load/migration cycles cannot duplicate the authored instance.

This is a general authored-instance reconciliation rule. Do not add a Memory-Stone-specific migration branch.

For `memoryStone_01`, a pre-Memory-Stone compatible save must gain exactly one stone in the Village temple. A save that already contains `memoryStone_01` somewhere else must preserve that saved instance there.

## Architecture constraints

- `ActionRegistry` remains the single formal-action execution path.
- Item definitions grant actions; they do not execute code.
- Effect IDs resolve only through an engine-owned allowlist/registry.
- HumanController and AIController consume the same canonical `view.available_actions` contract.
- Public events and private feedback remain separate normalized action-result channels.
- Existing transactional migration behavior remains authoritative; extend tests rather than introducing a parallel migration system.

## Acceptance criteria

- An owned item with a valid authored `useAction` grants `use_item` in `view.available_actions`.
- The options identify the concrete usable item instance and expose its authored action label.
- Submitting an item ID not offered by the current canonical view is rejected.
- `report_memory_counts` reports the exact current recent/long-term entry counts before its own feedback is enqueued.
- The successful physical use is publicly observable without memory counts.
- Only the actor receives the natural-language memory-count feedback.
- Human- and AI-controlled actors use the same action/effect semantics.
- The effect is read-only with respect to existing memory records and item state.
- A pre-Memory-Stone compatible save gains exactly one `memoryStone_01` at its new authored starting location.
- A save already containing `memoryStone_01` preserves its saved placement/state.
- Repeated migration/save/load does not duplicate the stone.
- No code branches on `memoryStone_01` or the Memory Stone definition name to perform migration or execute the effect.
